# Submission lock iteration — 2026-11-09

Base PR #1 head 5b13c0a; Actions run 42573534412 succeeded on Node 20/24 and Ubuntu/Windows. Reviewed source, tests, privacy iteration and draft PR. Selected the previously identified cross-process stale-lock race: two contenders could both inspect a dead owner, and a delayed unlink could remove a newer owner's lock. The old process probe also treated any error as proof of death.

Decision: do not automatically remove a submission lock. Exclusive creation fails closed for existing locks, including malformed or stale files; report other filesystem errors separately. README gives a manual recovery procedure that requires stopping all bridge processes first. This trades automatic recovery after a crash for avoiding unsafe stale-lock reclamation. The lock remains advisory and is not a defense against another local process deleting it. Node documents that exclusive creation may not work on network filesystems: https://nodejs.org/api/fs.html#file-system-flags. Runtime data should be on a local disk.

Tests: `npm run check` and `npm test`, Linux Node 24.22.1: 7/7 passed with simulated providers; new tests cover malformed and stale lock preservation and two concurrent bridge processes sharing a data directory, with one task admitted. This is a targeted concurrency test, not proof across all schedules or filesystems. No live provider, credentials or billing used. Check CI on this commit for Windows and Node 20.

Still open: the separate stale-job worker PID check treats all process-check errors as dead and is vulnerable to PID reuse and timing; it can cause an active job to be marked failed and must be redesigned and tested before claiming a robust one-task guarantee.
